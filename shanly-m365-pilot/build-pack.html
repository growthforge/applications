For IT, in a minute

  • What it is: a SharePoint list that works out each complaint's due dates by formula, a daily Power Automate flow that reminds the owner in Teams, and an approval step before any letter is sent. Copilot drafts letters; it never sets a date or sends anything.
  • Smallest useful version: the list and the daily reminder only. The confirmation card, the letter approval and the automated AI step are optional layers.
  • Licensing: standard connectors only (Outlook, SharePoint, Teams, Approvals). The automated AI step would need Copilot Credits and a Dataverse environment, so it waits for a licensing check and a DPIA.
  • Ownership and failure: a service account with co-owners, a solution outside the default environment, run-failure alerts and a daily "clock ran" message.
  • Not verified yet: behaviour after import into a tenant (calculated columns, card response paths, date formats). The handover note lists each item.

Check any date

The same engine as the mock-up. Enter when a complaint arrived and, if known, the reservation and completion dates.

Illustrative example: received Thursday 24 December 2026. The clock starts Tuesday 29 December 2026; acknowledge by Sunday 3 January 2027 (suggested send-by Thursday 31 December 2026); proposed pathway by Friday 8 January 2027; full assessment by Thursday 28 January 2027; next steps by Tuesday 23 February 2027.

// Expected dates were worked out by hand from Shanly Homes' published rules and checked
// against a calendar; bank holidays are England and Wales (GOV.UK).
import test from 'node:test';
import assert from 'node:assert/strict';
import fs from 'node:fs';
import * as c from './clock.js';

const bh = JSON.parse(fs.readFileSync(new URL('./bank-holidays-england-wales.json', import.meta.url)));
const H = c.holidaySet(bh.dates);

test('published example: received Monday, initiation Tuesday', () => {
  assert.equal(c.initiationDate('2026-11-02', H), '2026-11-03');
});
test('published example: received Saturday, initiation the next Monday', () => {
  assert.equal(c.initiationDate('2026-11-07', H), '2026-11-09');
});
test('received Sunday: initiation Monday', () => {
  assert.equal(c.initiationDate('2026-11-08', H), '2026-11-09');
});
test('received Friday: initiation Monday', () => {
  assert.equal(c.initiationDate('2026-11-13', H), '2026-11-16');
});
test('bank holiday Monday is skipped (Spring bank holiday 2026)', () => {
  assert.equal(c.initiationDate('2026-05-22', H), '2026-05-26');
});
test('Easter 2026: Good Friday and Easter Monday are skipped', () => {
  assert.equal(c.initiationDate('2026-04-02', H), '2026-04-07');
});
test('Christmas 2026: 25 Dec and the substitute Boxing Day (28 Dec) are skipped', () => {
  assert.equal(c.initiationDate('2026-12-24', H), '2026-12-29');
});
test('New Year 2027: received 31 Dec, 1 Jan is a bank holiday, initiation Monday 4 Jan', () => {
  assert.equal(c.initiationDate('2026-12-31', H), '2027-01-04');
});

test('all four stage dates from a Monday receipt', () => {
  const s = c.schedule('2026-11-09', H);
  assert.equal(s.initiation, '2026-11-10');
  assert.deepEqual(s.stages.map((x) => x.due), ['2026-11-15', '2026-11-20', '2026-12-10', '2027-01-05']);
});
test('a promise due on a Sunday must go by the Friday before', () => {
  const ack = c.schedule('2026-11-09', H).stages[0];
  assert.equal(ack.due, '2026-11-15');
  assert.equal(ack.sendBy, '2026-11-13');
});
test('a promise due on a working day can go that day', () => {
  const pathway = c.schedule('2026-11-09', H).stages[1];
  assert.equal(pathway.due, '2026-11-20');
  assert.equal(pathway.sendBy, '2026-11-20');

Intake, the daily clock and letter approval, written as step-by-step recipes with the exact actions and expressions.

Status: designed for Microsoft 365 and written from Microsoft's published documentation. The JSON parts are validated against Microsoft's published schemas (see CHECKS.md); nothing has been imported into a tenant and no flow has been run. Every step below is to be built and checked in a test environment with IT before any real email is processed.

These three cloud flows keep the dates in the complaints register. The dates themselves come from rules, never from AI: each rule here has a matching function in engine/clock.js and a test in engine/clock.test.mjs (table at the end).

Prerequisites

  • The SharePoint site with the two lists from sharepoint/complaints-register.site-script.json ("Complaints register" and "UK bank holidays"), and the bank-holiday list filled for at least the current and next year (see HANDOVER.md, yearly refresh).
  • A Power Platform environment other than the default environment, with a solution to hold the three flows, their connection references and environment variables (HANDOVER.md, ownership). Build the flows inside that solution.
  • A service account (not a person's account) for the connections, with:
  • Full Access and Send As on the complaints shared mailbox. Exchange Online describes Full Access as the permission to open the mailbox and Send As as the permission to send from it, and says both are needed for normal shared mailbox use [L20]. Microsoft's connector reference notes that new permissions can take about two hours to replicate before the flow can use them [L1].
  • Edit rights on the two lists (through the Complaints Team SharePoint group).
  • Membership of the Complaints Team in Teams.
  • The Workflows app allowed in the Teams admin centre. Microsoft's Teams connector reference says the posting actions need it [L3].

Conventions used below

  • Action names matter: expressions refer to actions by name, with spaces replaced by underscores. Rename each action exactly as shown in bold (for example Received UK date is referenced as outputs('Received_UK_date')).
  • All dates passed between steps are text in the form yyyy-MM-dd, the same form the engine uses. ISO dates compare correctly as text, and less(), greater() and lessOrEquals() all accept strings [L5].
  • Microsoft's expression reference does not say whether if() evaluates only the branch it returns [L5]. Every expression here is written to be safe either way: where a branch would fail on an empty value, coalesce() gives it a harmless stand-in.
  • Where a value comes from an action whose outputs Microsoft documents as dynamic (the Teams card response, the AI Builder prompt), the recipe names the dynamic content. Check the exact path in the outputs of the first test run before relying on a written expression.

Flow 1: Complaints intake

Goal: every email to the complaints mailbox gets a UK-time received date and an initiation date by the published rule, then a person decides the type. Anything that might be a complaint is logged; only a person can decide that it is not.

1.1 Trigger

  1. In the solution, select New > Automation > Cloud flow > Automated. Name it "Complaints intake".
  2. Choose the trigger When a new email arrives in a shared mailbox (V2) (Office 365 Outlook). Microsoft's data policy list names this connector Microsoft 365 Outlook [L19].
  3. Original Mailbox Address: the ComplaintsMailbox environment variable.
  4. Folder: Inbox.
  5. Include Attachments: No. Only with Attachments: No.

The trigger returns the message as Microsoft Graph defines it, including Received Time (receivedDateTime), From, Subject, Body, Body Preview, Message Id and Internet Message Id [L1].

Add Get items on the Complaints register, renamed Already logged, with Filter Query SourceEmailId eq '@{triggerOutputs()?['body/internetMessageId']}' and Top Count 1, then a Condition @greater(length(body('Already_logged')?['value']), 0) whose yes branch is Terminate (Cancelled). The internet message ID is used rather than the message ID because Graph changes a message's id when it moves to another folder [L6].

1.2 Received date in UK time

  1. Add Compose, rename it Received UK date:

``text convertFromUtc(triggerOutputs()?['body/receivedDateTime'], 'GMT Standard Time', 'yyyy-MM-dd') ``

Why: Microsoft Graph returns receivedDateTime in UTC [L6]. In British Summer Time an email that arrives at 00:30 on Saturday UK time is recorded as 23:30 UTC on Friday. Without the conversion the clock would treat a Saturday complaint as a Friday one and start a working day early. GMT Standard Time is Windows' name for the UK time zone, "(UTC) Dublin, Edinburgh, Lisbon, London" [L21], and it follows British Summer Time.

  1. Add Compose, rename it Received UK time (shown on the card):

``text convertFromUtc(triggerOutputs()?['body/receivedDateTime'], 'GMT Standard Time', 'ddd d MMM yyyy, HH:mm') ``

1.3 Bank holidays

  1. Add Get items (SharePoint), rename it Get bank holidays. Site Address: SiteUrl. List Name: UK bank holidays. Top Count: 500. No filter is needed: the list holds about eight dates a year.
  2. Add Select (Data Operation), rename it Holiday dates. From: the value of Get bank holidays. Switch Map to text mode and enter:

``text convertFromUtc(item()?['HolidayDate'], 'GMT Standard Time', 'yyyy-MM-dd') ``

The result is a plain list of dates such as ["2026-05-25", "2026-08-31"]. Converting to UK time before keeping the date part gives the right calendar date whether SharePoint returns a date-only value as midnight UTC or as UK midnight expressed in UTC. Check the raw value in the first test run.

1.4 Next working day (the initiation date)

The published rule: "The complaints initiation date is the first working day after a complaint is received", and public holidays are not working days.

  1. Add Initialize variable: Name Candidate, Type String, Value outputs('Received_UK_date'). Variables can only be declared at the top level of a flow, not inside loops or conditions [L8].
  2. Add Do until, rename it Next working day. Power Automate runs the actions inside the loop first and then checks the condition [L7], which is exactly the rule: start from the day after receipt and keep going until the day is a working day.
  3. Inside the loop add Compose, rename it Next date: addDays(variables('Candidate'), 1, 'yyyy-MM-dd')
  4. Then Set variable: Candidate = outputs('Next_date'). (Composing first keeps the Set variable value from referring to its own variable.)
  5. Loop condition (advanced mode):

``text @and( not(equals(dayOfWeek(variables('Candidate')), 0)), not(equals(dayOfWeek(variables('Candidate')), 6)), not(contains(body('Holiday_dates'), variables('Candidate'))) ) ``

dayOfWeek() returns 0 for Sunday and 6 for Saturday [L5]; contains() checks an array for a value [L5].

  • Leave Count at 60 and Timeout at PT1H, the defaults [L7]. The longest real run is five iterations (for example, received Thursday 24 December 2026: Christmas Day, the weekend and the substitute Boxing Day are skipped).
  • Add Compose, rename it Initiation date: variables('Candidate')
  • Add Compose, rename it Clock starts (for the card): formatDateTime(outputs('Initiation_date'), 'dddd d MMMM yyyy', 'en-GB')

Worked example (engine test "bank holiday Monday is skipped (Spring bank holiday 2026)"): received Friday 22 May 2026; Saturday, Sunday and Monday 25 May (bank holiday) are skipped; initiation date Tuesday 26 May 2026.

Flow 2: Daily clock

Goal: every weekday morning, find the next unsent commitment for each open complaint, remind its owner when it is due soon, escalate it when it is overdue, keep NextUpdateDue current and post a short message so that silence is noticed.

2.1 Trigger

  1. New > Automation > Cloud flow > Scheduled, named "Complaints daily clock". In the Recurrence trigger [L13]:
  2. Interval 1, Frequency Week.
  3. Time zone: the UK entry (Dublin, Edinburgh, Lisbon, London), so that 07:30 means UK time. Check the first run after the clocks change.
  4. On these days: Monday to Friday. At these hours: 7. At these minutes: 30.

The flow also runs on bank holidays. That is harmless: the counts stay true and the due-soon rule already counts working days.

  1. Add Initialize variable twice: DueSoonCount (Integer, 0) and OverdueCount (Integer, 0). They go here, before the scope, because variables can only be declared at the top level of a flow, not inside scopes, conditions or loops [L8].
  2. Add Scope, rename it Try. Everything in sections 2.2 and 2.3 and step 12 goes inside it.

2.2 Today, and a working-day calendar built once

  1. Compose Today: convertFromUtc(utcNow(), 'GMT Standard Time', 'yyyy-MM-dd')
  2. Get bank holidays and Holiday dates: as Flow 1, steps 5 and 6.
  3. Select, rename it Calendar. From: range(0, 31). Map (text mode): addDays(outputs('Today'), sub(item(), 10), 'yyyy-MM-dd'). This lists the 31 days from ten days ago to twenty days ahead.
  4. Filter array, rename it Working days. From: body('Calendar'). Condition (advanced mode):

``text @and(not(equals(dayOfWeek(item()), 0)), not(equals(dayOfWeek(item()), 6)), not(contains(body('Holiday_dates'), item()))) ``

  1. Filter array Working days after today: from body('Working_days'), condition @greater(item(), outputs('Today')).
  2. Compose Due soon cutoff: body('Working_days_after_today')[2], the third working day after today.

Why this works: the engine calls a commitment "due soon" when its send-by date is no more than two working days away. The send-by date is the latest working day on or before the due date, so that test is the same as "the due date falls before the third working day after today". the pack validator (results in CHECKS.md) checks this equivalence against the engine for complaints received on every day from December 2025 to November 2028. Building the calendar once avoids a loop inside a loop.

The prompt

Rules that always apply:
1. Never write a date, a day of the week or a number of days. Where the letter needs a date, use exactly one of these placeholders: [ACK_DUE], [PATHWAY_DUE], [ASSESSMENT_DUE]. Where it needs a timescale for an action, write [TIMESCALE: the action] for the team member to fill in.

5. Do not repeat health, disability or other personal circumstances from the email, beyond a brief acknowledgement where the customer has raised them. Never include anyone else's personal details.

- PROPOSED PATHWAY: thank the customer; restate the issues briefly; set out the proposed steps to resolve each issue, taken only from the notes, each with who will act and [TIMESCALE: the step]; explain that a full assessment, including the current position, will follow by [ASSESSMENT_DUE]; invite the customer to comment on the proposed steps.

How it is measured

eval/cases.jsonl holds illustrative emails with the expected answer, written separately from this prompt. eval/score.mjs scores any model's answers. What matters most, in order:

  1. every possible emergency flagged (target: all of them);
  2. no formal complaint labelled as anything else (the dangerous error);

  4. every answer valid against the schema;
  5. type accuracy and date extraction overall.

Five-person usability test (week 4)

Why five: Jakob Nielsen's article "Why You Only Need to Test with 5 Users" (Nielsen Norman Group, 18 March 2000, https://www.nngroup.com/articles/why-you-only-need-to-test-with-5-users/, read 3 Nov 2026) argues that testing with about five people finds most usability problems, and that several small rounds of testing are better than one large one. So: five people now, fix, and test again if the trial is kept.

Who: five people who would use it: coordinators, complaint handlers and the team lead. Thirty minutes each, one at a time, at their own desk with Outlook and Teams open.

Material: the test site with illustrative complaints only (fictional customers and developments). No real customer data.

How: I read each task aloud and say nothing else. I ask the person to think aloud. I note what they do, not what I hoped they would do.

Tasks

  1. "An email has just arrived in the complaints mailbox. Deal with it in Teams." (The illustrative email arrived on the Friday before a bank holiday Monday.)
  2. "When must this complaint be acknowledged, and has it been?" (In the register.)
  3. "You have a reminder in Teams. Find the complaint it is about."
  4. "Draft the acknowledgement for this complaint and send it for approval." (Using the saved Copilot prompt and the register.)
  5. "This email is a new defect report for the customer portal, not a complaint. Deal with it."
  6. "Which complaints need something from the team this week?"

What to observe

  • Time to finish each task, and whether it was finished without help.
  • Where people hesitate, what they read twice, and what they miss on the Teams cards.
  • Whether they check the initiation date and the due dates or accept them without looking, and whether they understand why a bank holiday moved the start.
  • How they read the labels: in particular whether "Due soon" (two calendar days in the list) and the reminder (two working days) cause confusion.
  • Whether "Not a complaint" feels safe to press, and whether anyone presses it by mistake.
  • Any placeholder left in a draft, and whether the approval step catches it.

Questions afterwards

  1. What was the most confusing moment?
  2. What would you change first?
  3. How does this compare with how you keep these dates today?
  4. Is there anything here you would not trust, and why?
  5. What would stop you using this every day?
  6. If we kept only one part, which should it be?

Findings are written up the same day as a short list: problem, how many of the five hit it, the change proposed. The Complaints Team lead decides which changes are made before week 7.
